What goes in the kit.
What doesn't.

Fifteen ideas arrived in one day. This is the filtered version — kept, deferred, or thrown out, with the reason. Ricardo's instruction: "I am just telling everything that comes to mind. You need to organize the ideas and throw away what won't work."

In the kit App-level, not kit Later Thrown out

The distinction that does most of the work here:

A starter kit ships things every project needs on day one. A capability only some apps need is a module they install, or an app-level build — not kit weight. Most of today's ideas are excellent and belong in an app, not in the thing every repo inherits.

1 Architecture

The only irreversible category. Everything here is nearly free upfront and a rebuild later.

In the kit

Agentic-native — "create once, use many"

Every capability is a callable procedure; the agent is never a second-class caller. The one decision that cannot be retrofitted. Already the rule; tRPC is already the layer. Costs nothing to hold, costs a rewrite to add later.

In the kit

iOS-friendly, works at most screen sizes

Same character: cheap upfront, expensive to retrofit. 44px targets, safe areas, and the rule that a phone layout is designed, not derived by narrowing a desktop one.

In the kit

Thin, quarantined agent glue — but no chosen SDK

The protection against "OpenAI ships a better SDK" is not a wrapper. It is that the tools live in procedures, so the runtime is a few hundred lines you can throw away. The kit ships the pattern; the app picks the SDK when it needs one. CMA stays on the table — for apps that run seldom, its per-session pricing is negligible and it removes infrastructure work.

2 Authentication

Added last, and it should have been first. This is where money is leaking right now.

"I am spending thousands of dollars getting WorkOS to work… it is happening right now with H-Analytics. It still does not work."

Every app needs login. Every login should look and behave the same. Paying to solve it again per project is the single clearest case for a starter kit that exists — and unlike everything else on this page, it is costing money today.

In the kit

One auth module, two modes

Open — anyone can register (consumer apps). Closed — a person must be pre-approved before they can register, and an unknown email is turned away rather than silently creating an account (enterprise, investor portals). Ricardo is right that this is not conceptually hard. It is expensive because it is re-derived every time, exactly like the empty design contract.

In the kit

The whole flow, not just the login box

The cost is never the login screen. It is invitation, email verification, password reset, expired links, session expiry mid-action, org switching, role changes, the first-run experience for an invited user, and what a rejected user sees. Each is a screen and an edge case, and each is where the days go.

Diagnose first

Is WorkOS actually the right choice?

Chosen in decision 0001 and currently failing expensively at H-Analytics. I do not yet know why, and I will not promise a module wrapping a tool that may be the problem. If the failure is integration complexity, a kit module fixes it permanently. If it is WorkOS itself, no wrapper saves it. One diagnosis answers this, and it should happen before anything is built.

3 Design

The highest-value unbuilt thing on this list, and it needs no agent to start.

In the kit

A populated design contract

docs/design-system.md already exists in the kit — as an empty template. "The AI messes up something that was working" is the direct consequence of that file being blank: an agent with no record of past decisions re-derives them, and re-deriving is indistinguishable from breaking. Fill it in once, with Ricardo. That hour is what stops the repetition.

In the kit

Theme mechanism + a curated set

shadcn themes are named CSS variables; 42 exist ready to install. The kit ships the mechanism and a short curated list — not the catalogue.

Thrown out

User-selectable themes in every app

Wrong default for client-facing products. An investor picking Cyberpunk for the Obra Pía portal dilutes the brand and produces screenshots that don't look like your company. Revised: user-selectable in internal tools; admin-set per organisation in client-facing apps, from a family that keeps the brand recognisable. Same mechanism, different authority.

Later

Designer agent

Genuinely wanted, but sequenced after the contract. An agent with taste and no memory makes the second pain worse while feeling like it addresses it. Build the memory, then the agent that reads it.

4 Onboarding

Arrived last and it removes work rather than adding it — the best kind of idea.

"Better than a tour would be questions… where you get to know the user and the company and the brand, and from that you could infer a theme… But I do not want to create the questionnaire."

In the kit

An interview instead of a tour

Right on the merits. Tours get skipped; conversations get answered. And a tour teaches the app while an interview teaches the app about you — one is a cost to the user, the other is a trade.

Thrown out

A Typeform-style component

We are already building a conversational interface. Rebecca is the interview — one question at a time, in the panel, on first login. Building a separate one-question-at-a-time widget alongside a chat panel is the same component twice.

This also settles something left open earlier: a copilot in every app was hard to justify, because most apps have no obvious first job for one. Now it does. Rebecca's first conversation with every user is the onboarding interview, which means she earns her place on day one instead of waiting for someone to need her.

In the kit

Declare what needs knowing; the agent decides how to ask

Ricardo does not want to write questionnaires, and should not have to. But an agent cannot invent what an app needs to know. The split: each app declares its settings — what they are, what they affect, what a good answer looks like. The agent turns that into an interview and decides order, phrasing and when to stop. A list of settings is something you write once and is useful anyway; a questionnaire is not.

With one change

Inferring the theme from brand answers

Do not apply an inferred theme — propose it. Getting it wrong makes a user's first impression of the app a theme they dislike, chosen by a machine, with no obvious way to undo it. Show two or three that fit what they said, pre-selected, and let them confirm. Same intelligence, none of the risk, and picking from a shortlist feels good where being assigned one does not.

In the kit

Onboarding belongs to the auth module

It fires immediately after first login, and it is where an invited user's first-run experience lives — already on the auth list. Same module, not a separate one.

5 The copilot

App-level

Rebecca — the copilot panel

She already exists in the taxonomy as Rebecca · AI Co-Pilot. A rich copilot is a large build that needs real usage to be good. Putting one in every app by default produces several mediocre copilots instead of one excellent one. Ships to one app, gets good, then spreads. The kit ships the architecture that makes her possible, not her.

Later

Copilot drives the UI

The interesting half, and the part that needs real design: navigation happens in the browser, so some tools resolve server-side and some client-side, and the model must see one list. Mechanism confirmed to exist. Not day-one.

Thrown out

Model-chosen UI components

The obvious way to stream charts into a chat — Vercel's streamUI — is explicitly not recommended for production by Vercel's own docs. The alternative is better anyway: tools return data, our code renders. The model never picks components.

5 Modules

All good ideas. None of them kit material — they are things an app installs.

App-level

Document management

The most genuinely recurring of the four. Strongest candidate for the first real module, and the presigned-upload work from Obra Pía is most of the plumbing already.

App-level

Photo enhancement + album

Settled: both original and render are kept, and the render always carries a mark saying it is enhanced. Non-destructive, the pairing is a real relation rather than a filename convention, and the mark must travel into exports and reports — the case most likely to be forgotten.

Thrown out

Admin-assignable animation per modal and process

Over-built for the value. This is a settings screen, a data model, and a resolver — so that an admin can choose which spinner appears where. Almost nobody will ever change it, and the default will be right. Revised: animations are part of the theme, chosen once by design. If one app genuinely needs per-process assignment, that app builds it.

6 Memory and learning

Later

Retrieval + corrective memory

Buildable today with what is already chosen — Voyage embeddings on pgvector. Corrective memory (a user's correction persists and applies next time) is cheap and the thing users actually notice. Real, just not first.

Thrown out

Pinecone

Same capability as pgvector + Voyage, which are already in the stack, at the cost of a fourth data store. Pinecone was right when it was the only option.

Later

"Dreaming" / consolidation

Unverified — I do not know which product this refers to and will not guess. There is real research on memory consolidation and idle-time computation, but the standing rule after fabricating a package name is to check rather than recall. Needs a source before anything is designed around it.

7 Communications and voice

Later

Email in and out, SMS, RCS

Verified as available: Resend does support inbound, and Twilio RCS is generally available. One planning fact worth knowing — RCS sender onboarding is manual brand verification, not an API call. Calendar time, not developer time. Nothing to build until an app needs it.

Thrown out

Evaluating voice vendors now

ElevenLabs, Retell, and whoever else — any comparison made today is stale before it ships. The one thing that matters is already true: voice is just another caller of the same procedures, which is affordable precisely because the architecture holds. Re-research at the point of decision, not before.

8 Infrastructure

Thrown out

Cloudflare Workers

Not because they couldn't cope — the limits are generous and API waits don't count against CPU. Because they solve nothing here. Edge latency, zero idle cost, spike absorption: none is a problem you have. For SMS webhooks, carrier latency dominates. Buys a second deployment story and a second thing to debug, for a theoretical benefit. R2 stays; Railway alone stands.

Thrown out

Large files in git

Nothing over 5MB, enforced by CI rather than remembered. Git keeps every version of every binary forever in every clone, and deleting it later reclaims nothing. The kit itself is currently in violation at 180MB of brand assets — that needs moving to R2.

9 What to build first

Ten idea drops today. One repo equipped. Zero apps.

The equip test found seven real defects in four hours — none visible in any document. Building is how you find out what's wrong; specifying is how you feel like you're finding out.

My recommendation changed when auth came up. It was: build the Manual app. Auth is worth more, because it is bleeding money this week and the Manual is not.

First

Diagnose what is actually failing at H-Analytics

Hours, not days. Nothing should be built around WorkOS until it is known whether WorkOS is the problem. The answer decides whether the auth module is a wrapper or a replacement.

Then

The auth module — open and closed modes, every screen

Solved once, correctly, including the invitation and recovery flows where the days actually go. Every project after inherits it.

Proven in

The Manual app

It needs a login anyway. So it becomes the proving ground for the auth module rather than a separate piece of work — and it is still the first app built under the parity and iOS rules. One build, two things proven.

Everything else waits. New ideas go on a list, unread, until there is a URL to open.
